# douyin-laike-data-audit-skill

> 抖音来客／本地推 **经营数据统计审计**技能。
> 把公式、自检题和对账规则做成**程序校验**：模型负责解释和提出假设，**关键数字由计算程序产生**。

---

## 这个技能解决什么问题

经营者拿到后台导出的一堆表，最想要的是一句结论；而最容易发生的，是用**错误的分母**、
**错误的时间窗口**或**未经验证的关联**，造出一份看起来很完整的报告。

典型错误（这个技能会逐条拦住）：

| 错误 | 后果 |
|---|---|
| 把各组 ROI 直接平均 | 花 99% 预算的组只影响一半结论 |
| 把"今天核销额 ÷ 今天成交额"当核销率 | 分母根本不是同一批订单 |
| 一单两券时把每行"购买数量"相加 | 券数翻倍 |
| 订单表 join 核销表后直接汇总金额 | 订单金额被重复累计 |
| 分母为 0 时显示"0%" | 把"不可计算"伪装成"表现很差" |
| 用"总成交额 ÷ 消耗"当广告新增 ROI | 把全域成交算成广告功劳 |
| 3000 笔订单当成 3000 个独立样本 | 统计推断完全无效 |

**最高原则：宁可明确报告"数据不足"，也不能用错误分母、错误时间窗口或未经验证的关联，制造看似完整的结论。**

技能遵循 Agent Skills 约定（一个目录 + `SKILL.md`），可放在两处：

```bash
# 用户级（推荐：任何项目的新对话都能用上）
git clone https://github.com/womeng2018-dotcom/douyin-laike-data-audit-skill.git \
  ~/.dsh/skills/douyin-laike-data-audit

# 或工作区级
git clone https://github.com/womeng2018-dotcom/douyin-laike-data-audit-skill.git \
  "<你的工作区>/.dsh/skills/douyin-laike-data-audit"
```

也可以把 `SKILL.md` 的内容直接粘到别的 AI（ChatGPT / Claude / Gemini / 其他 agent）的
系统提示词里 —— 它的设计目标之一就是"能当系统提示词用"。
`references/11-统一规范全文.md` 是单文件全文版，最适合这一用途。

环境要求：**Python 3.9+**，脚本**只用标准库**；读 `.xlsx` 需要 `openpyxl`（可选）。

## 三十秒上手

```bash
cd <技能目录>

# 1. 开工前自检（8 个规范案例，必须 8/8 PASS，退出码 0）
python3 scripts/selftest.py

# 2. 数据契约体检：每张表"一行是什么"、时间范围、主键、缺失、重复
python3 scripts/contract.py 订单表.csv 核销表.csv 退款表.csv

# 3. 关联审计：防金额放大（一单多券最容易在这里翻倍）
python3 scripts/reconcile.py join --left 订单表.csv --right 核销表.csv \
    --left-key 订单ID --right-key 订单ID \
    --left-values 订单实收金额 --right-values 核销金额

# 3b. 正确路径：事件表先按对象聚合，再与对象表 1:1 关联
python3 scripts/build_cohort_table.py \
    --orders 订单表.csv --events 核销表.csv \
    --key 订单ID --event-time 核销时间 --out-col 首次核销时间 \
    --out 订单级批次表.csv

# 4. 分组回加对账
python3 scripts/reconcile.py group --file 门店明细.csv --group 门店 \
    --values 消耗 成交金额 --total 消耗=7911.96 成交金额=989159.80

# 5. 同批次同观察年龄的核销率（成熟条件 t0 + H <= T 由程序把关）
python3 scripts/cohort.py --file 订单级批次表.csv --t0 支付时间 \
    --event 首次核销时间 --cutoff "2026-09-10 12:00:00" \
    --hours 24 --dedupe 订单ID --curve 24,72,168

# 6. 生成固定格式报告，把程序算出的数字注入进去（不要手抄）
python3 scripts/cohort.py ... --json > rate.json
python3 scripts/make_facts.py --rate-json rate.json \
    --label "24小时窗口内核销订单比例" --source "订单表+核销表" --out facts.json
python3 scripts/report.py --scaffold --facts facts.json --out 报告.md

# 7. 全部测试 + 端到端演示
python3 tests/run_tests.py
bash examples/end_to_end_demo.sh
```

**退出码约定**：`0` = 通过；`2` = 判定失败／口径不足／必须人工介入
（关联金额放大、分组回加对不上、分母为 0、事件时间列解析全失败等）。
**看到 2 就不要出结论，先解决它。**

## 设计原则

1. **关键数字由程序产生。** 每个 `Result` 都带着分子、分母、公式、口径、不可计算原因，
   可以直接嵌进报告，做到"可复算、可追溯"。
2. **分母为 0 显示"不可计算"，不是 0%。** 这是 `metrics.safe_div` 的硬约束。
3. **自检题变成断言。** 8 个案例写成 `selftest.py`，错就是非零退出码，
   而不是一份"看起来很完整"的报告。
4. **对账规则变成闸门。** 关联后金额放大 → `reconcile.py` 直接判
   "失败-禁止使用该结果"并返回退出码 2。
5. **证据只有四个标签**：`已对账事实`／`观察性差异`／`待验证假设`／`数据不足`。
   **不使用主观"可信度 87%"或任意机会分。**
6. **只用标准库，不改动原始文件。**

## 8 个自检案例的正确答案

| # | 案例 | 正确答案 |
|---|---|---|
| 1 | 总体 ROI（100 元 ROI 3 ＋ 10000 元 ROI 1） | `10300/10100 ≈ 1.0198`，**不是 2** |
| 2 | 一单两券（支付 200，核销两行各 100，购买数量都写 2） | **1 笔订单、2 张核销券、核销金额 200 元**；不是 2 笔／4 张／400 元 |
| 3 | 观察窗口（A 满 24h 已核销、B 满 24h 未核销、C 只 3 小时） | **1/2 = 50%**，不是 1/3 |
| 4 | CTR 4% → 5% | **提高 1 个百分点**，相对提升 **25%**；不是"提升 1%" |
| 5 | 两天卖 6 万、消耗 400 | **不能**算 60000/400=150 并称为广告新增 ROI → **数据不足** |
| 6 | 9 月核销 100 张，其中 30 张 8 月购买 | 9 月**批次**分子 = 70；9 月**门店接待量** = 100 |
| 7 | 实付 98、实收 100、退款 99 | **不能**把 98−99=−1 当亏损；先查优惠、补贴、费用口径 |
| 8 | 3000 笔订单、2 天投放 | 独立单位是 **2 天**，不是 3000；**不能**证明广告有效 |

跑 `python3 scripts/selftest.py` 可以看到每个案例的完整推导、正确公式与常见错误做法。

## 适用范围与已知限制（诚实申报）

**总纲**：本技能**不能替你确认业务口径**。程序只能保证"按你给的口径算得对"，
口径本身对不对必须回后台核对（见 `references/13` 第四节的 10 个问句）。
下面每一条都是实际会碰到的边界，不是免责声明。

### 数据契约体检（contract.py）

- **粒度只给候选**：「一行是什么」由列名关键词推断，证据会一起列出，但**永远需要人工确认**。
  英文缩写或无明显 ID 字样的列会退化成"文本"。
- **类型识别靠关键词**：列名里没有"金额／元／消耗／实付"等词的金额列（例如只叫 `revenue`
  或 `fee`）识别不到；请把这类列显式告诉分析者。
- **科学计数法不可逆**：`7.00123E+15` 这种被 Excel 转过的 ID，程序只能发现"精度已丢失"，
  **无法还原原始 ID**，必须重新导出为文本。
- **时间格式有边界**（实测）：`08/01/2024`（美式月/日/年）**不会被解析**，会计入"解析失败"——
  这是刻意的，因为无法与 `日/月/年` 区分。请确认你的导出到底用哪种格式。
  支持 `2024/08/01`、`2024-08-01`、`20240801`、`2024年8月1日` 及带 `T` 的 ISO。
- **重复检测是字符串级"整行完全重复"**：空格、大小写、全半角差异不算重复；
  也**不检测业务重复**（如同一券码两条核销记录）。
- **"未结束的部分日"是启发式**（最后一天金额 < 其他天中位数 50%），可能漏报或误报；
  "日期缺口"只在无事件 ID 列的汇总表上告警，事件明细表刻意不报警，因此可能漏掉真实断层。
- **Excel**：默认只读第一个工作表（多 sheet 需 `--sheet`）；读缓存值，公式无缓存会显示为空；
  `.xls` 直接拒绝；合并单元格的表头会出现 `(空列N)`，**不会自动还原双层表头**。
- **性能未优化**：全量扫描，百万行级导出会慢且吃内存，未做流式。

### 关联审计（reconcile.py）

- **键匹配只忽略首尾空白**（实测）：`O1` 与 `o1` 被当作**两个不同的键**，
  补零差异（`123` vs `0123`）、全角半角差异同样不会匹配。
  跨表关联前务必确认键的写法一致，否则会得到大量"未匹配"。
- **空键有意不参与关联**（否则空键互配会产生虚假关联），一律计入"未匹配 + 键缺失(空)"。
- **未匹配原因三分类是启发式**（占位符／日期形态／键形态），只能提示"疑似时间范围不同"，
  **不能证明**。
- **金额解析边界**：不支持 `1.2万`（会报错要求先换算）、不支持欧式 `1.234,56`；
  含字母的文本列不会被当成金额（否则 `C1` 会被解析成 `1`）。
- **两条容差语义不同**：关联放大 = `关联后 > 关联前×(1+容差)`；
  分组回加 = `|差额| < 容差` 才算一致（默认 0.01，所以差一分钱也会报）。
- **未覆盖**：≥3 张表的链式关联审计；按日期维度自动裁剪时间范围；券状态（有效/已退款）过滤。

### 成熟批次与口径（metrics.py / cohort.py）

- `cohort.py` 依赖"支付时间"字段存在且可解析；**解析失败会计数，不会静默丢弃**。
- 事件列的**时间语义 vs 存在语义会自动判定**：列里 ≥80% 的值能按时间解析才算时间列，
  否则改用"有值即命中"，并在报告里写明用了哪种语义。
  显式传 `--event-time` 可覆盖这个判定。
- **护栏只防错、不补数据**：分母为 0 时输出"不可计算"；事件时间列解析全失败时拒绝输出 0% ——
  这两种情况下**你会拿到一个错误提示，而不是一个数字**，这是设计如此。
- 金额口径、补贴与对账规则**必须由人提供**：未对账时不计算净收入与利润。

### 因果与实验

- 技能只提供**证据分级与防线**（四个标签、因果防线、样本单位防线），
  **不提供实验设计**：随机分配、主指标、最小业务差异、停止规则仍需人来定。
- 达到预算上限可以停投，但技能不会把"停止花钱"当成"已证明素材无效"。

### 环境

- 只支持 `csv` / `tsv` / `txt` / `xlsx`（`xlsx` 需 `openpyxl`，可选依赖）；
  `.xls` 旧格式请先另存为 xlsx 或 csv。
- 需要 **Python 3.9+**；不需要 pandas / numpy / scipy。
- 编码自动判定顺序为 `utf-8-sig → utf-8 → gbk → gb18030 → utf-16`，极端文件请用 `--encoding` 兜底。
